# FlyWire 全图跨机器实测 · 2026-09-06

27（Mac Studio）和 23（Linux）均已完成完整加权图的正确性与性能测试。Rust AOT 在两台机器上均降低了运行时间和原生内存占用。两个后端都成功运行，没有出现 C++ OOM。

## 测试口径

- 同一 FlyWire v783 完整图：139,255 个神经元、15,091,983 条有向加权连接，代表 54,492,922 个生物突触接触。保留孤立节点，不使用五接触阈值。
- 同一 float64 LIF 模型、种子 783、dt 0.1 ms、模拟 1 秒；每个后端测试 1、4、8、16 线程，预热后交错重复 5 次。
- 下表耗时为仿真加记录的中位数，不包含预处理、编译、程序启动及结果文件写出。峰值内存取五次原生子进程 RSS 的最大值，不含 Python 和编译器。
- 真实连接拓扑配统一兴奋性 LIF 动力学；没有拟合果蝇生理、递质正负号、形态或行为，也不测试 STDP。生物接触数不能表述为逐接触模拟的边数。
- 数据来自 [FlyWire v783.0 官方发布](https://zenodo.org/records/10676866)，CC BY 4.0；相关论文：[Dorkenwald 等，2024](https://www.nature.com/articles/s41586-024-07558-y)。

## 各后端最佳已测配置

为避免以 C++ 较慢的高线程配置夸大优势，分别选择每个后端在 1、4、8、16 线程中的最低中位数：

| 主机 | Rust 最佳 | C++ 最佳 | 加速比 | 最佳配置原生内存 Rust / C++ |
| --- | ---: | ---: | ---: | ---: |
| 27 · M1 Ultra | 0.767 秒 / 16 线程 | 3.873 秒 / 1 线程 | 5.05× | 400.95 / 829.05 MiB |
| 23 · EPYC 9454 × 2 | 0.839 秒 / 16 线程 | 4.555 秒 / 8 线程 | 5.43× | 317.19 / 768.29 MiB |

Rust 从 1 到 16 线程的自身提速：M1 Ultra 为 3.18×，EPYC 为 4.78×。两者在最佳配置下均能用不到 1 秒的仿真循环时间完成 1 秒模型时间；包含加载和输出的进程总时间另列于原始 JSON，不能把这句话扩大为端到端实时。

本机 M3 的历史同模型结果作为参照：1 线程 Rust / C++ 为 2.205 / 3.547 秒（1.61×）；4 线程为 1.574 / 3.509 秒（2.23×）。各机 CPU、操作系统与 C++ 编译器不同，不能把跨主机差异全部归因于硬件。

## 正确性与回归

- 两台机器的完整 Rust 回归均通过：136 项测试、113 个子测试；新增测量器及相关定向回归在两台机器均为 9 项通过。
- 最终 80 次正式重放以及预热均校验了全部最终电压、不应期状态、全部脉冲 ID/时间/计数和 16 个神经元的电压轨迹。每次同机 Rust/C++ 差分的最大误差均为零。
- 每次模型产生 3,853,674 个脉冲；Rust 记录 462,577,974 次加权边事件投递。
- 跨主机比较：M1 Ultra 与本机 M3 的记录完全一致；Linux 的全部脉冲、轨迹及不应期状态也一致，最终电压最大差异为 2.220446049250313e-16。

Linux 本轮明确限制在同一插槽的 16 个物理核心内，未测试 96 核或 192 线程全机吞吐。两台机器均使用 Brian2 2.10.1.post199 和 NumPy 2.5.2。

原有 Linux `wait4` 统计包含 fork 后、exec 前继承自 Python 父进程的 RSS，使 Rust 单线程误记约 444 MiB。独立 `/usr/bin/time -v` 核验得到 300 MiB。已修复为先启动一个只加载标准库的小型监督进程，再由它启动并测量原生程序；最终五轮全部使用该流程。监督进程启动不计入原生进程 wall time。首轮报告保留用于审计，其 Linux RSS 不应用作最终内存结论。
