# 跨主机／多物理 GPU BPTT 验收方案

2026-10-03。本文是待执行的跨主机方案，未分配跨主机资源、未连接测试或生产主机，
也不构成跨主机 GPU 验收证据。用户随后授权的新版单 L4 作业另记于
[RK/refractory 验收](mpi-evidence/training-rk-refractory-20261003/README.md)。

## 资源与启动条件

最小跨主机配置为两台隔离 Linux 测试主机，每台一张独立 NVIDIA GPU；优先相同型号
L4、相同驱动及 CUDA 编译工具链。同一台机器的两张卡可以单独验证多物理 GPU，不能
替代跨主机验证。多个 MPI rank 共享同一 GPU 的现有结果也不满足这两项验收。

准备时需要两台测试主机的可连接标识、相互可达 IP、隔离工作目录、可用 GPU UUID、
相同 CPU ABI 和 MPI 分发版本。先确认控制通道与 MPI 数据通道可用；不能把启动两个
独立云容器当作已建立多主机 MPI。已有 Teleport CPU launcher 可供适配，不修改服务配置。

费用方案须等资源确定后提交：如使用两张 L4，建议整个测试组最多 15 分钟、无测试重跑，
函数执行窗口对应 30 GPU 分钟；供应商的初始化、构建、存储及替换容器计费另按实际配置核实。
这不同于此前单张 L4 的单次授权，不能沿用。已有测试主机也须明确允许的占用范围。

2026-10-03 核对 [Modal 当前集群文档](https://modal.com/docs/guide/multi-node-clusters)：
clustered function 必须使用整节点 GPU，例如 H100:8，不能将 H100:4 当作合法节点。
因此上述两张 L4 只是通用最小硬件方案，并不是已确认可在 Modal 集群上申请的配置。
若选两节点 H100:8，将分配 16 张 GPU，15 分钟执行窗口对应 240 GPU 分钟；这远大于
当前单 L4 范围，不能自动扩大。优先确认是否已有两台各一张卡的测试主机；使用 Modal
整节点方案则需先准备对应执行器、核实报价并明确新的总额度。本轮没有启动该集群。

按 2026-10-03 查询的 [Modal 公布单价](https://modal.com/pricing)，H100 为
0.001097 美元/GPU/秒，16 张卡运行 900 秒仅 GPU 部分约 **15.80 美元**。
这是计算估算而非账单硬上限：CPU、内存、初始化、容器收尾和平台替换可能另外计费；
函数 timeout 也不等同于整个应用计费生命周期。公布的 Starter GPU 并发额度为 10，
不足以运行 16 张卡；实际账号额度与集群资格尚未确认，不能假设可用或自动升级套餐。

## 预检与身份证据

1. 在 GPU 测试前，验证真实 2/4 ranks 的 MPI 身份、有序求和及 CPU 串行数值对照。
   全部 rank 必须具有唯一全局 rank 和一致 world size，禁止 singleton MPI 假成功。
2. 每台主机的原生执行器、MPI shim、CUDA 库、请求和 rank launcher 分别计算 SHA-256；
   完全一致后才继续。还需记录源码清单、编译器、驱动和 GPU ABI `v4r3`。
3. 每个 rank 记录 hostname、全局/本地 rank、world size、可见设备映射及实际选择设备的
   CUDA UUID、PCI bus ID。UUID 应由使用相同设备选择逻辑的 CUDA runtime 探针取得；
   单靠 `nvidia-smi` 设备清单或逻辑编号 0 不能证明进程使用了哪张物理卡。
4. 验收器同时检查两个不同主机和至少两个不同物理 UUID，并检查每个 rank 的真实 GPU
   dispatch。设备不可用、映射冲突或 CUDA 执行失败必须使测试失败，不能回退 CPU。

## 数值与恢复矩阵

使用小型合成输入和确定性网络，不上传真实训练数据。执行下面各项时保留相同初值、
权重、数据和源码，对照 CPU 串行以及单卡 CUDA 结果。

| 项目 | 测试布局 | 通过条件 |
| --- | --- | --- |
| 原生多状态 BPTT | 两主机共 2/4 ranks；含耦合状态和一般复位 | 脉冲完全一致；损失、全部权重和神经元参数梯度、完整初态 VJP 及最终状态符合容差 |
| 空 owner | 两主机共 8 ranks，小网络 | 所有 rank 完成，无死锁；空 owner 不影响归约 |
| 新前端 | RK2/RK4、混合积分、固定时长 refractory 的部分保持 | 对照独立前向/VJP；计时状态精确，物理状态符合容差 |
| 两次训练 | full/TBPTT、detach 两种模式 | 比较完整 optimizer 状态、权重、全部物理状态及计时器 |
| 保存与恢复 | 含非零计时器的中途快照；启动全新 MPI 进程组 | 同一布局重放与未中断继续执行逐项一致，源码和库指纹一致 |
| 有界失败 | 测试启动前的错误设备映射或不匹配指纹 | 拒绝启动，保留诊断；不提交部分训练状态 |

CPU 与 GPU 的浮点对照使用当前 GPU 回归的 `atol=6e-6, rtol=4e-4` 上限，optimizer
等字段沿用现有更严格检查。硬脉冲、整数计时器、步数及结构要求精确相等。挑选远离
阈值不稳定边界的固定样例；发生差异先定位原因，不能靠事后放宽容差获得通过。
同布局全新进程恢复要求精确一致；跨布局恢复不宣称逐位等价。

## 执行器适配与收尾

现有 `tools/verify_native_training_crosshost.py` 仍是 CPU 验证入口。本轮已补上 v4 的
完整 `final_state` 接续、辅助状态与完整初态 VJP 校验、非有限数拒绝和整数状态精确
检查；10 项本地测试通过，日志见
[工具测试](mpi-evidence/training-rk-refractory-20261003/crosshost-helper.log)。
这不代表工具已在两台主机上重跑，也不代表 GPU 验收通过。它仍缺少 GPU UUID、CUDA
库指纹、逐 rank 设备绑定、GPU 数值容差和单次执行锁，不能直接用作 GPU 验收器。
资源确定后先完成这些适配并本地测试，再执行云端作业。

预先固定测试矩阵和总时间限制；失败即记录，不自动重新执行测试。异常退出须回收
所有 rank/容器并核实无残留 GPU 任务。保存逐 rank 日志、JUnit/结构化结果、请求及
输入哈希、主机/设备身份、二进制和源码指纹、启停时间以及最终资源状态。只有这些
证据齐全且矩阵通过，才能将“跨主机／多物理 GPU”改为已验证。

这项验收不测试性能加速比或大模型扩展性。当前每个 rank 仍保存完整模型、输入和
tape，验证正确性不能推导出分布式内存节省。
