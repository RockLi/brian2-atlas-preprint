# Potjans–Diesmann 2014 full-scale milestone

This milestone answers a narrow but important feasibility question: can the Rust
backend construct and execute the full Potjans–Diesmann cortical microcircuit on
an Apple Silicon workstation without materialising roughly 300 million Python
objects or JSON records?

The answer is yes. The current implementation constructs 298,880,968 recurrent
synapses for 77,169 neurons and executes the model on an M1 Ultra with a peak
resident set of about 3.11 GB. Current B2IR v21 (building on the v20 topology
milestone) and the public `rust_standalone` Device carry fixed-total procedural topology, per-edge clipped-normal constant
parameters, and clipped-normal heterogeneous delays without Python edge arrays.
The complete eight-population, 55-projection model now runs through an ordinary
Brian2 `Network`; the original native runner remains a compact feasibility and
regression baseline.

## Model represented

The runner uses the eight populations, population sizes, recurrent connection
probability matrix, fixed-total connection rule, clipped normal weights and
delays, current-based exponential synapses, LIF parameters, refractory period,
DC background drive, and optimised initial membrane-potential distributions of
the public PD14 reference implementation.

| Quantity | Value |
| --- | ---: |
| Populations | 8 |
| Neurons | 77,169 |
| Non-empty recurrent projections | 55 |
| Recurrent synapses | 298,880,968 |
| Time step | 0.1 ms |
| Refractory period | 2 ms |
| Numerical storage | f64 neuron state, f32 static weights, u16 delay ticks |

The generated connectivity is deterministic for a fixed seed. Fixed-total
sampling allows autapses and multapses, matching the selected reference rule.
The published reference code is available from the
[INM-6 microcircuit-PD14-model repository](https://github.com/INM-6/microcircuit-PD14-model).

## Compact construction

Each projection is stored source-major as:

- `source_count + 1` u32 offsets;
- one u32 target per edge;
- one f32 weight per edge;
- one u16 delay tick per edge.

The source index and a second CSR edge-index array are implicit. The full
topology therefore requires 2,991,195,776 bytes (2.786 GiB) before small runtime
state and queue overhead. Construction uses two deterministic passes: the first
counts edges per source, and the second fills the source-major arrays. At no
point does Python receive or serialise the edge list.

## Reproduction

From `brian2-rust`:

```sh
cargo build --release --locked --bin pd14

# Exact scale and memory estimate; does not allocate the topology.
./target/release/pd14 --full --estimate-only

# Construct all recurrent projections but do not simulate.
./target/release/pd14 --full --build-only --maximum-gib 4

# Stable short benchmark.
./target/release/pd14 --full --duration-ms 100 \
  --warmups 1 --repetitions 7 --maximum-gib 4

# Full 500 ms presimulation plus 1,000 ms simulation duration.
./target/release/pd14 --full --duration-ms 1500 \
  --warmups 0 --repetitions 1 --maximum-gib 4
```

The default invocation deliberately runs a 1% smoke model. `--maximum-gib`
checks the exact topology estimate before allocation. `--output FILE` writes the
versioned `b2-pd14-benchmark-v1` JSON report; it contains only aggregate results,
not topology or monitor payloads.

## Apple Silicon results (2026-09-05)

Both machines used native `aarch64-apple-darwin` release binaries. The M1 Ultra
run used rustc 1.98.1, LLVM 22.1.8. Timings are wall-clock times with one process
and the current serial simulation loop; no GPU or multi-thread event routing is
included yet.

| Host | Full topology build | 100 ms median | 100 ms spread | Event throughput | 1,500 ms simulation |
| --- | ---: | ---: | ---: | ---: | ---: |
| Apple M3, 8 cores, 16 GB | 11.68 s | 1.0627 s | 3.40% | 85.89M/s | 16.4117 s |
| Apple M1 Ultra, 20 cores, 128 GB | 13.79 s | 1.0682 s | 0.65% | 85.45M/s | 15.9492 s |

On the M1 Ultra, topology-only peak RSS was 2,996,404,224 bytes and the 100 ms
benchmark peak RSS was 3,111,501,824 bytes, with zero swaps. The 1,500 ms run
delivered 1,382,279,859 events at 86.67 million events/s.

The M1 Ultra also completed the community benchmark's minimum performance
duration of 10 s of model time with spike recording disabled. The simulation
body took 106.568 s (`qRTF = 10.657`) and delivered 9,236,654,397 events at
86.67 million events/s. Including the 13.801 s topology build, process wall time
was 120.43 s. Maximum RSS was 3,299,590,144 bytes with zero swaps: 10.01 bytes
per recurrent synapse for the topology alone and approximately 11.04 bytes per
synapse for the whole process at peak.

The final M1 Ultra population rates were:

| Population | Rust rate (Hz) | Reference rate (Hz) |
| --- | ---: | ---: |
| L2/3E | 0.825 | 0.903 |
| L2/3I | 2.782 | 2.965 |
| L4E | 4.168 | 4.414 |
| L4I | 5.619 | 5.876 |
| L5E | 7.501 | 7.569 |
| L5I | 8.315 | 8.633 |

These rates are a strong model-level sanity check, but they are not a formal
trajectory comparison: the counter RNG intentionally does not reproduce the
reference implementation's random bit stream.

## Evaluation status

The community benchmarking recipe separates accuracy, performance, and
resources. The unified Device comparison is recorded in
[PD14_COMPARISON.md](PD14_COMPARISON.md), with the dual-socket Linux repeat in
[PD14_LINUX_COMPARISON.md](PD14_LINUX_COMPARISON.md) and the constrained 16 GB
Apple Silicon feasibility test in [PD14_LOCAL_16GB.md](PD14_LOCAL_16GB.md).
The purpose-built NEST 3.10 comparison, including equal-thread and full-machine
OpenMP scaling, is in [PD14_NEST_COMPARISON.md](PD14_NEST_COMPARISON.md):

| Axis | Current evidence | Status |
| --- | --- | --- |
| Model construction | Exact population sizes, projection count, recurrent edge count, bounded distributions and deterministic topology tests | Passed for the implemented DC-input variant |
| Statistical accuracy | Full per-neuron rates, ISI-CV, and 250-neuron 2 ms spike-count correlation distributions against ten official PyNEST realisations | 22/24 Rust and 23/24 C++ diagnostic entries within reference p95 |
| Performance | Same Device model on Rust and C++ standalone, 10 s with monitors disabled, with simulation/build timing separated | Rust target-owner runtime: 33.93 s on M1 Ultra/16 threads and 32.91 s on EPYC/32 threads for 9.47B delivered events |
| Memory | Child and frontend peak RSS for both implementations | Final target-owner child RSS is 7.67 GB; still 1.7x below NEST despite the additional incoming owner CSR |
| NEST CPU baseline | Same fixed-total/DC-input model on M1 Ultra and dual-socket EPYC | Rust is 1.99x faster than NEST on M1 Ultra; NEST remains 6.44x faster at its 96-core EPYC optimum |
| Energy | Not measured at the wall outlet | Missing |

The completed comparison discards 500 ms and measures 10 s, matching the public
T10 reference archive. It compares the complete single-neuron firing-rate and
ISI-CV distributions plus the 250-neuron, 2 ms-binned correlation distributions.
The reference repository also provides longer-duration datasets; a formal
multi-seed acceptance protocol remains future work, so the reference-p95 flag is
documented as a diagnostic rather than an official pass/fail rule.

## Device integration status

The initial Device path is explicit because Brian2 `connect(p=...)` specifies
independent Bernoulli trials, whereas PD14 uses one global fixed edge count with
replacement. Reinterpreting `p` would silently change model semantics:

```python
import brian2_rust

synapses = Synapses(source, target, on_pre="v_post += jump", delay=1*ms,
                    namespace={"jump": 0.1})
brian2_rust.connect_fixed_total(synapses, 10_000_000, seed=1234)
```

`len(synapses)` reports the logical edge count, while `_synaptic_pre` and
`_synaptic_post` remain unallocated. B2IR stores only `kind=fixed_total`, count,
and seed; reference and AOT generate the same deterministic source-major order
inside Rust. The AOT serial representation stores source offsets and one u32
target per edge; parallel target ownership adds an edge-id partition only when
multiple workers are actually active.

The ordinary Device implementation is `examples/pd14_device.py`. It has two
frontends: Rust uses only procedural descriptors, while C++ standalone
materialises the fixed-total endpoint arrays because public Brian2
`connect(p=...)` has different Bernoulli semantics. Both use redraw rather than
clamp for out-of-bound normal weights and delays, matching the public PyNEST
implementation. `examples/pd14_compare.py` compares full single-neuron rate,
ISI-CV and 250-neuron/2-ms spike-count-correlation distributions against the ten
official PyNEST realizations.

`examples/nest_pd14_benchmark.py` constructs the same shape directly through
PyNEST and records construction, `Prepare`, simulation, end-to-end time, kernel
counters, and RSS. `examples/pd14_compare.py` accepts its report/statistics as
an optional third backend. NEST is currently the CPU-concurrency performance
target: the Rust backend's advantage over serial C++ standalone does not extend
to NEST's mature virtual-process scaling.

Remaining work is performance-oriented: the general Device currently stores
generated weights as f64 and delays as `usize`. Heterogeneous-delay primary
`on_pre` is now target-partitioned, and projections sharing a source window are
fused into one route dispatch; Linux additionally has automatic worker affinity
and parallel first-touch for the large procedural arrays. The compact runner's
f32/u16 layout, pooled event capacity and complete memory estimator therefore
remain optimization targets, not separate user-facing execution paths. The
post-optimization Linux measurements are recorded in
[PD14_LINUX_COMPARISON.md](PD14_LINUX_COMPARISON.md).
